# clang 20 as a CUDA-to-PTX compiler

## What it is

clang can compile CUDA C++ for NVIDIA GPUs without `nvcc`. With
`--cuda-device-only -S` it stops after the device-side code generation and
writes **PTX text**. That PTX is the input format of Kamui: every PTX file in
the Kamui PTX corpus is produced by clang 20 from our own CUDA sources, never
by `nvcc`. `nvcc` and `ptxas` are used only to collect evidence and to check
syntax (see [ptxas.md](ptxas.md)).

Internally clang compiles the device side as a separate compilation for the
triple `nvptx64-nvidia-cuda`, links NVIDIA's `libdevice.10.bc` (math library
as LLVM bitcode) into the module, runs the LLVM optimiser and the NVPTX
backend, and prints PTX. The CUDA headers from the toolkit are used for
declarations; clang wraps them with its own `__clang_cuda_runtime_wrapper.h`.

## Where it runs

**Dev container** (`kamui-isa-dev:0.2`, clang 20 from apt.llvm.org on top of
`nvidia/cuda:12.8.1-devel-ubuntu24.04`; see [devcontainer.md](devcontainer.md)).
No GPU is needed. The H100 job image also has clang-20, but corpus PTX is
always generated in the dev container so that it is reproducible and committed.

## Version pinned

- `Ubuntu clang version 20.1.8 (++20250804090239+87f0227cb601-1~exp1~20250804210352.139)`,
  that is LLVM `release/20.x` at commit `87f0227cb601` (tag `llvmorg-20.1.8`).
- CUDA toolkit 12.8.1 at `/usr/local/cuda` (used for headers and
  `libdevice.10.bc`).
- PTX ISA 8.7, forced with `--cuda-feature=+ptx87`. PTX 8.7 is the version
  that clang 20 maps CUDA 12.8 to, and it is the version Kamui pins.
  Open question: the pin is confirmed only once the first H100 job reports the
  CUDA and driver versions (see [h100-jobs.md](h100-jobs.md)).

## Commands we use

The canonical corpus command (all flags verified in the dev container):

```bash
clang++-20 -x cuda --cuda-gpu-arch=sm_90a --cuda-device-only -S -O2 \
  --cuda-feature=+ptx87 --cuda-path=/usr/local/cuda \
  -Wno-unknown-cuda-version \
  -o k.ptx k.cu
```

| Flag | Why |
|---|---|
| `-x cuda` | Treat the input as CUDA even if the extension is unusual |
| `--cuda-gpu-arch=sm_90a` | Target H100 with the arch-accelerated features (`wgmma`, `setmaxnreg`). Writes `.target sm_90a` |
| `--cuda-device-only` | Compile only the GPU side; no host object |
| `-S` | Stop at assembly, that is PTX text |
| `-O2` | Required. At `-O0` the CUDA wrapper functions are not inlined (see gotchas) |
| `--cuda-feature=+ptx87` | Force `.version 8.7`, independent of the installed CUDA ([clang `Cuda.cpp` lines 673 to 677](https://github.com/llvm/llvm-project/blob/llvmorg-20.1.8/clang/lib/Driver/ToolChains/Cuda.cpp#L673-L677)) |
| `--cuda-path=/usr/local/cuda` | Use exactly this toolkit for headers and libdevice |
| `-Wno-unknown-cuda-version` | Silence `CUDA version 12.8 is only partially supported` (expected, see below) |

Other commands:

```bash
# See what clang really runs (the -cc1 command line):
clang++-20 -### -x cuda --cuda-gpu-arch=sm_90a --cuda-device-only -S -O2 \
  --cuda-feature=+ptx87 --cuda-path=/usr/local/cuda -o k.ptx k.cu

# Device-only cubin in one step (clang calls ptxas itself), with ptxas -v:
clang++-20 -x cuda --cuda-gpu-arch=sm_90a --cuda-device-only -c -O2 \
  --cuda-feature=+ptx87 --cuda-path=/usr/local/cuda -Xcuda-ptxas -v -o k.cubin k.cu

# LLVM IR instead of PTX (to see which llvm.nvvm intrinsics were used):
clang++-20 -x cuda --cuda-gpu-arch=sm_90a --cuda-device-only -S -emit-llvm -O2 \
  --cuda-feature=+ptx87 --cuda-path=/usr/local/cuda -o k.ll k.cu

# PTX from hand-written LLVM IR:
llc-20 -mtriple=nvptx64-nvidia-cuda -mcpu=sm_90a -mattr=+ptx87 -o k.ptx k.ll
```

For the corpus, prefer the two-step path (clang to PTX, then `ptxas`
separately, see [ptxas.md](ptxas.md)), because the PTX file is the artifact we
commit.

PTX reaches the corpus by one of four routes: plain CUDA (`cuda`), clang
builtins such as `__nvvm_*` (`builtin`), inline PTX in `asm volatile`
(`inline-asm`), or hand-written LLVM IR through `llc-20` (`llvm-ir`).

## Input formats

- CUDA C++ (`.cu`). `extern "C"` on kernels keeps the PTX entry names
  unmangled (`toy` instead of `_Z3toyPKiPiPj`); use it for every corpus kernel
  so the runner can find the entry by name.
- LLVM IR (`.ll`) for `llc-20`, with `target triple = "nvptx64-nvidia-cuda"`
  and kernels marked through `!nvvm.annotations` (`!{ptr @k, !"kernel", i32 1}`).
  Example: [wgmma_intrinsics.ll](../examples/cuda/wgmma_intrinsics.ll).

## Output formats

PTX text. Annotated header of a real output (`toy.cu` below):

```
//
// Generated by LLVM NVPTX Back-End          <- producer
//

.version 8.7                                 <- PTX ISA version, from --cuda-feature=+ptx87
.target sm_90a                               <- from --cuda-gpu-arch
.address_size 64                             <- 64-bit generic pointers

.visible .entry toy(                         <- extern "C" kernel, unmangled
	.param .u64 .ptr .align 1 toy_param_0,   <- kernel params live in .param space
	...
{
	.reg .pred 	%p<4>;                       <- virtual registers, unlimited; ptxas allocates
	.reg .b32 	%r<26>;
	.reg .b64 	%rd<12>;
	.shared .align 4 .u32 _ZZ3toyE7cta_sum;  <- __shared__ variable "demoted" into the kernel
```

clang also prints comments such as `// %bb.0:`, `// begin inline asm`,
`// end inline asm` and `// -- End function`. Ignore them when diffing.

## Worked example

The example sources are in [docs/examples/cuda/](../examples/cuda/). All of
them are our own code. The commands on this page and in
[ptxas.md](ptxas.md), [cuobjdump.md](cuobjdump.md) and
[nvdisasm.md](nvdisasm.md) assume this working directory inside the dev
container:

```bash
tools/dev.sh                          # shell in the dev container, at the repository root
mkdir -p build/examples/cuda && cd build/examples/cuda
EX=../../../docs/examples/cuda        # the example sources
```

Source ([toy.cu](../examples/cuda/toy.cu), comments shortened):

```cuda
extern "C" __global__ void toy(const int *in, int *out, unsigned *mask_out) {
  __shared__ int cta_sum;
  int tid = threadIdx.x;
  if (tid == 0) cta_sum = 0;
  __syncthreads();                                   // bar.sync 0
  int v = in[blockIdx.x * blockDim.x + tid];
  for (int off = 16; off > 0; off >>= 1)             // warp butterfly reduction
    v += __shfl_xor_sync(0xffffffffu, v, off);
  unsigned am;
  asm volatile("activemask.b32 %0;" : "=r"(am));     // inline asm, kept by volatile
  if ((tid & 31) == 0) {
    atomicAdd(&cta_sum, v);                          // shared-memory atomic
    mask_out[blockIdx.x * (blockDim.x / 32) + tid / 32] = am;
  }
  __syncthreads();
  if (tid == 0) atomicAdd(out, cta_sum);             // global atomic, result unused
}
```

Command and output (dev container, 2026-10-29):

```
$ clang++-20 -x cuda --cuda-gpu-arch=sm_90a --cuda-device-only -S -O2 \
    --cuda-feature=+ptx87 --cuda-path=/usr/local/cuda -o toy.ptx $EX/toy.cu
clang++-20: warning: CUDA version 12.8 is only partially supported [-Wunknown-cuda-version]
```

Key PTX lines (annotated):

```
	cvta.to.global.u64 	%rd1, %rd6;            // param pointer -> global address
	mov.u32 	%r1, %tid.x;                       // special register read
	setp.ne.s32 	%p1, %r1, 0;
	@%p1 bra 	$L__BB0_2;                         // divergent if, as predicated branch
	st.shared.u32 	[_ZZ3toyE7cta_sum], %r4;
$L__BB0_2:
	bar.sync 	0;                                 // __syncthreads()
	ld.global.u32 	%r9, [%rd9];
	shfl.sync.bfly.b32	%r10, %r9, 16, 31, -1;    // __shfl_xor_sync: lane^16, clamp 31, mask 0xffffffff
	...                                            // loop fully unrolled: 16, 8, 4, 2, 1
	// begin inline asm
	activemask.b32 %r5;                            // copied verbatim from asm()
	// end inline asm
	atom.shared.add.u32 	%r23, [%rd11], %r3;     // atomicAdd on __shared__ (generic pointer was resolved to .shared)
	st.global.u32 	[%rd4], %r5;
$L__BB0_4:
	bar.sync 	0;
	ld.shared.u32 	%r24, [_ZZ3toyE7cta_sum];
	atom.global.add.u32 	%r25, [%rd2], %r24;     // result unused, but clang still emits atom (ptxas turns it into RED)
	ret;
```

Without `--cuda-feature` the same file comes out identical (`.version 8.7`),
because CUDA 12.8 is detected and mapped to `+ptx87`. The flag matters for
any other CUDA version.

The SASS for this kernel is annotated in [cuobjdump.md](cuobjdump.md) and
[nvdisasm.md](nvdisasm.md).

### What clang 20 does with atomic orderings and scopes (measured)

Sources [atomics.cu](../examples/cuda/atomics.cu) and
[scoped_fence.cu](../examples/cuda/scoped_fence.cu); PTX produced by the
canonical command:

| CUDA source | PTX emitted by clang 20 | Comment |
|---|---|---|
| `atomicAdd(p, 1)` (result used) | `atom.global.add.u32` | no `.sem`, no `.scope`: PTX default is `.relaxed.gpu` |
| `__atomic_fetch_add(p, 1, __ATOMIC_SEQ_CST)` | `atom.global.add.u32` | **ordering dropped** |
| `__scoped_atomic_fetch_add(p, 1, __ATOMIC_ACQ_REL, __MEMORY_SCOPE_WRKGRP)` | `atom.global.add.u32` | **ordering and scope dropped** |
| `__scoped_atomic_fetch_add(p, 1, __ATOMIC_RELAXED, __MEMORY_SCOPE_SYSTEM)` | `atom.global.add.u32` | **system scope weakened to gpu** |
| `__atomic_compare_exchange_n(..., __ATOMIC_ACQ_REL, __ATOMIC_ACQUIRE)` | `atom.global.cas.b32` | ordering dropped |
| `__atomic_load_n(p, __ATOMIC_ACQUIRE)` | `ld.acquire.sys.global.u32` | ordering kept, scope `sys` (C11 default) |
| `__atomic_store_n(p, v, __ATOMIC_RELEASE)` | `st.release.sys.global.u32` | ordering kept |
| `__atomic_load_n(p, __ATOMIC_RELAXED)` | `ld.relaxed.sys.global.u32` | |
| `__atomic_thread_fence(__ATOMIC_SEQ_CST)` | `fence.sc.sys` | |
| `__scoped_atomic_thread_fence(__ATOMIC_ACQ_REL, __MEMORY_SCOPE_WRKGRP)` then `(__ATOMIC_SEQ_CST, __MEMORY_SCOPE_DEVICE)` | a single `fence.sc.sys` | **scope ignored**, fences merged |
| `__threadfence_block()`, `__threadfence()`, `__threadfence_system()` | `membar.cta`, `membar.gl`, `membar.sys` | |
| `__nvvm_atom_cta_add_gen_i(p, 1)` (builtin) | `atom.cta.add.s32` (generic address) | the only way to get a scope on an RMW from clang 20 without inline asm |

Consequence for the corpus and the litmus suite: **scoped and ordered RMW
atomics (`atom.acquire.gpu`, `atom.release.cta`, `atom.acq_rel.cluster`,
`red.release`) and scoped fences (`fence.acq_rel.cta`, `fence.sc.cluster` from
C++) cannot be produced from portable C++ atomics with clang 20.** Corpus
entries for them must use the `__nvvm_atom_{cta,sys}_*` builtins (scope only,
relaxed) or inline asm
(`asm volatile("atom.acq_rel.gpu.global.add.u32 %0,[%1],%2;" ...)`).
This also tells `kamui-llvm` that LLVM IR `atomicrmw ... syncscope("block")
acq_rel` currently reaches PTX with the ordering lost. The Kamui spec must not
take clang 20's lowering as a reference for the memory model; the formal PTX
memory model is the reference (see [dartagnan.md](dartagnan.md) and
[alloy.md](alloy.md)).

### Math and floating point (measured, [math.cu](../examples/cuda/math.cu), [fp.cu](../examples/cuda/fp.cu))

| Source / flag | PTX |
|---|---|
| `a*b + c` (default) | `fma.rn.f32` (clang contracts by default for CUDA) |
| `a*b + c` with `-ffp-contract=off` | `mul.rn.f32` then `add.rn.f32` |
| `a / b` (default) | `div.rn.f32` |
| `a / b` with `-ffast-math` | `div.approx.f32` |
| any of the above with `-fcuda-flush-denormals-to-zero` | `.ftz` added (`fma.rn.ftz.f32`, `div.rn.ftz.f32`, `sqrt.rn.ftz.f32`) |
| `sinf(x)` | libdevice `__nv_sinf` inlined into a long sequence (no call at `-O2`) |
| `__sinf(x)`, `__expf(x)` | `sin.approx.f32`; `ex2.approx.ftz.f32` after a multiply |
| `tanhf(x)` | libdevice sequence (never `tanh.approx`) |

Corpus rule: each floating-point corpus entry fixes `-ffp-contract` and
`-fcuda-flush-denormals-to-zero` explicitly in its YAML descriptor, because
they change the PTX instruction being tested. nvcc also fuses by default
(`--fmad=true`), so goldens from nvcc-built references would agree with the
clang default.

## How to keep a feature from being optimized away

1. Inputs come from global memory (kernel arguments), never from constants;
   otherwise LLVM folds the operation.
2. Every result is stored to global memory.
3. Inline asm uses `asm volatile(...)`, plus a `"memory"` clobber when it has
   memory side effects (fences, barriers, `wgmma.fence`). Without `volatile`,
   an asm whose outputs are unused is deleted.
4. Compile with `-O2` and check the PTX for the expected instruction. The
   corpus build greps each corpus PTX for the feature's opcode string and
   fails if it is missing.
5. Watch for ptxas-level rewrites too: an `atom` whose result is unused becomes
   `RED` in SASS; a warp-uniform `atom` becomes a warp-aggregated `ATOM` by the
   leader lane (see [cuobjdump.md](cuobjdump.md)). That is fine for PTX goldens
   but matters for SASS evidence and for atomics determinism.

## `-nocudalib` and `-nocudainc`

Measured with `toy.cu` and `math.cu`:

- `-nocudalib` (alias of `-nogpulib`): libdevice is not linked. `toy.cu`
  still compiles (it needs no math). `math.cu` compiles to PTX but contains
  `.extern .func ... __nv_sinf`, `__nv_fast_sinf`, `__nv_fast_expf`;
  `ptxas` then fails with `ptxas fatal : Unresolved extern function '__nv_sinf'`.
  Do not use it for the corpus.
- `-nocudainc` (alias of `-nogpuinc`): clang does not add the CUDA include
  paths **and** does not pre-include `__clang_cuda_runtime_wrapper.h`, so
  `__global__`, `__shared__`, `threadIdx`, `blockIdx` and `__shfl_xor_sync`
  are all unknown (`error: unknown type name '__global__'`). Only useful with
  a self-contained header that defines the attributes and builtins yourself.
  Not used by kamui-isa.

## Warnings with CUDA 12.8

- `clang++-20: warning: CUDA version 12.8 is only partially supported
  [-Wunknown-cuda-version]`: printed on every compile (clang 20 lists 12.3 as
  fully supported, 12.8 as partially supported). Harmless for our use; silence
  with `-Wno-unknown-cuda-version`.
- A CUDA newer than 12.8 would produce `CUDA version X is newer than the
  latest partially supported version 12.8` and, without `--cuda-feature`,
  PTX 8.6. Always pass `--cuda-feature=+ptx87`.

## How kamui-isa uses it

- **PTX corpus**: clang 20 generates every corpus PTX file. The YAML
  descriptor of each entry records its extra clang flags (the common command
  above is fixed for the whole corpus) and the route (`cuda`, `builtin`,
  `inline-asm`, `llvm-ir`).
- **H100 goldens**: the same PTX is assembled by `ptxas` in the dev container
  ([ptxas.md](ptxas.md)) and JIT-loaded on the H100 ([h100-jobs.md](h100-jobs.md)).
- **Litmus tests on the H100**: they are written in inline PTX, because the
  orderings and scopes they need are not reachable from C++ with clang 20
  (see above, and [herd7-litmus7.md](herd7-litmus7.md)).
- **Two-way table** (`spec/ptx-table.md`): for each PTX instruction it records
  whether clang 20 emits it from normal code (CUDA, builtins or LLVM IR) or
  only from inline asm.

## Limitations and gotchas

- `-O0` output is not usable for the corpus: wrappers such as
  `__shfl_xor_sync` and `atomicAdd` stay as `.func` calls
  (`call _Z15__shfl_xor_syncjiii`), shuffle operands become registers instead
  of immediates, and atomics use generic addresses (`atom.add.u32` instead of
  `atom.shared.add.u32`).
- clang does not parse inline asm. Typos in asm strings are reported only by
  `ptxas`.
- `__shared__ alignas(8) T x;` is rejected by clang 20 ("an attribute list
  cannot appear here"); write `__shared__ T x __attribute__((aligned(8)));`
  or use a naturally 8-byte type.
- The `__nvvm_mbarrier_*_shared` builtins take
  `__attribute__((address_space(3))) long *`; cast explicitly:
  `typedef __attribute__((address_space(3))) long smem_i64;` then
  `(smem_i64 *)&bar`.
- With the host+device path (`-c` without `--cuda-device-only`), clang 20
  uses the new offload driver and embeds only the `sm_90a` cubin, no PTX
  (`cuobjdump -lptx` finds nothing). We do not rely on embedded PTX anyway.
- clang emits `.param .u64 .ptr .align 1` for pointer kernel parameters
  (PTX 5.1.6.3 `.ptr` attribute). Other producers (nvcc) omit `.ptr`; a PTX
  parser must accept both.
