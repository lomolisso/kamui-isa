# tests/corpus/

The PTX feature corpus. `catalog.yaml` lists every feature of PTX ISA 8.7 that matters for `sm_90a`: each
instruction, the modifiers that change what the ISA must do, the state spaces, the special registers and the
directives. Each feature is assigned to a Kamui extension family and a tier, or excluded with a reason.

The catalog is the list of work items for the rest of the project: every in-scope feature gets a small CUDA
micro-kernel here, its output on an H100 becomes a golden, and `spec/ptx-table.md` (generated from the catalog)
records how Kamui implements it.

## Layout

```
tests/corpus/
  catalog.yaml                     the master catalog, one entry per feature, sorted by id
  <family>/<feature>/              one micro-kernel per in-scope feature (added feature by feature)
    kernel.cu                      our own CUDA source (inline PTX allowed)
    kernel.ptx                     generated by clang 20; committed, never edited by hand
    entry.yaml                     launch configuration, inputs, outputs, expected PTX
```

## Catalog fields

| Field | Meaning |
|---|---|
| `id` | Stable feature id, lower case, dots kept from PTX, no type suffix: `shfl.sync.bfly`, `atom.global.add`. Special registers are `sreg.<name>`, directives `dir.<name>`, state spaces `space.<name>`, small whole programs `app.<name>`. When one mnemonic has sections in several chapters, a word tells them apart: `add.int`, `add.fp`, `add.half`. Axes of a modifier are spelled out: `atom.sem.acquire`, `atom.scope.cta`, `fence.sem.sc` |
| `kind` | `instruction`, `modifier`, `state-space`, `special-register`, `directive` or `application` |
| `opcodes` | PTX opcode prefixes this entry stands for, used by the coverage check against clang's opcodes (see below). Optional |
| `ptx_syntax` | Canonical syntax line, from the manual |
| `manual_section` | Section number and title in the PTX ISA 8.7 manual |
| `introduced_ptx`, `min_target` | Oldest PTX version and oldest target, from the section's "PTX ISA Notes" and "Target ISA Notes" (`all`: every target) |
| `family` | `base` (plain RV64 suffices) or one of the `Xkm` extensions of [docs/overview.md](../../docs/overview.md) |
| `tier` | Kamui tier 1 to 4 |
| `route` | How a CUDA kernel reaches the feature: `cuda` (plain CUDA C++), `builtin` (a clang `__nvvm_*` builtin), `llvm-ir` (only an LLVM intrinsic), `inline-asm` (only `asm volatile`) |
| `status` | `in-scope` or `excluded` |
| `exclusion_reason` | Why an excluded feature is out of scope |
| `entry` | Corpus directory of the micro-kernel; empty until it is written; `pending` (reason in `notes`) when it cannot be written yet |
| `tolerance_class` | How an output is compared with the H100: `exact`, `ulp:<n>`, `ftz`, `reduction` (order-dependent floating-point sums), `property:<name>` (non-deterministic values such as `%clock64`) |
| `notes` | What later work must know |

**One entry per value of an axis, not per combination.** An instruction is split only along axes that change what
the ISA must do (state space, scope, memory ordering, the operation of an atomic, shuffle and vote modes,
`.approx`). Each axis value gets one entry, tested on one representative form: `atom.global.add`,
`atom.shared.add`, `atom.sem.acquire`, `atom.scope.cta`, but not `atom.shared.acquire.cta.add`. Type variants
(`.u32`, `.s64`, `.f32`) stay in one entry; its kernel covers each type class the ISA must tell apart.

## Checks

```bash
python tools/catalog/check_coverage.py --all        # in the dev container, from the repository root
python tools/catalog/gen_table.py --check
```

NVIDIA publishes no machine-readable list of PTX instructions, so `check_coverage.py` compares the catalog with
three sources written independently of each other:

- **A, the manual's structure:** every instruction section of chapter 9.7, every special register (chapter 10),
  every directive (chapter 11) and every state space (5.1) has an entry.
- **B, clang 20:** every opcode the LLVM 20 NVPTX back end can print, plus the inline assembly of clang's CUDA
  headers, is covered: an entry's `opcodes` prefix matches it in whole dot components after type components are
  dropped (`shfl.sync.bfly` covers `shfl.sync.bfly.b32`).
- **C, the release notes:** every special register, directive, modifier and instruction named in chapter 12
  matches an entry.

The three sources are read from fact-only snapshots in `tools/catalog/snapshots/`, so the checks also run in CI.
Accepted mismatches are listed with a reason in `tools/catalog/coverage-exceptions.yaml`.

## Entries

Each in-scope feature has an entry directory `<family>/<id>/` (`::` in an id becomes `.`). Several catalog rows can
share one entry when its kernel exercises all of them (for example `dir.version` uses `app.vecadd`).

```
kernel.cu      our own CUDA C++ (or kernel.ll, LLVM IR, for features CUDA cannot spell, such as .maxnreg)
kernel.ptx     produced by tools/corpus/build.py; committed
entry.yaml     how to compile, launch and check the kernel
```

`entry.yaml` fields:

| Field | Meaning |
|---|---|
| `id` | The catalog id |
| `kernel` | The `extern "C"` kernel name |
| `compile` | `extra_flags` for clang on top of the common ones; optional `ptxas_flags` (for example `-c` for a module with external symbols) |
| `launch` | `grid`, `block` (three integers each), `cluster` (null or three integers), `dynamic_smem` (bytes) |
| `params` | Kernel parameters in order. `kind` is `input` (read only), `inout` (initialised, then read back), `output` (starts zeroed, read back) or `scalar` (passed by value, `value`). `dtype` is one of `u8 s8 u16 s16 u32 s32 u64 s64 f16 bf16 f32 f64`; buffers have a `count` of elements |
| `generator` | Initial contents of `input` and `inout` buffers: `iota` (`start`, `step`), `const` (`value`), `random` (`seed`, `low`, `high`), `file` (`path` in the entry directory) |
| `expect_ptx` | Regular expressions that must match `kernel.ptx`: proof that the feature survived compilation |
| `expect_ptxas` | Optional regular expressions that must match the `ptxas -v` output |
| `deterministic` | `false` when the output depends on scheduling (clocks, atomics return values) |
| `tolerance_class` | As in the catalog, and equal to it |
| `run` | `false` for a compile-only entry (for example `brkpt`); the reason is in `notes` |
| `notes` | What the H100 runner or a later check must know |

Generators run only in `tools/corpus/gen_inputs.py`, which writes `inputs.bin` (the `input` and `inout` buffers
in parameter order, raw little-endian, no padding) under `build/corpus/`. Runners read `inputs.bin` and never
reimplement the generators.

Floating-point entries state `-ffp-contract=on|off` and `-fcuda-flush-denormals-to-zero` or
`-fno-cuda-flush-denormals-to-zero` explicitly, so the PTX does not depend on compiler defaults.

```bash
python tools/corpus/build.py --all             # rebuild every entry and rewrite kernel.ptx (dev container)
python tools/corpus/build.py --all --check     # rebuild and compare with the committed kernel.ptx
python tools/corpus/build.py --all --lint      # no compiler: entry.yaml and expectations against kernel.ptx
python tools/corpus/gen_inputs.py --all        # inputs.bin for every entry
```

## Rules for kernels

- `extern "C" __global__`; inputs come from global memory and outputs go to global memory, so nothing is folded
  away. Thread-dependent data keeps the compiler from treating values as uniform.
- Race-free, with a deterministic output, or `deterministic: false` with a `property:` tolerance.
- Atomics test one address shared by all threads and one address per thread; returned values of the shared
  address are checked as a set.
- All PTX is produced by clang (or llc, for the few LLVM IR entries) from our own sources, never by nvcc and never
  copied from NVIDIA.
- `kernel.ptx` is always rebuilt by the pinned clang and PTX version, never edited by hand.
- No CUDA headers or NVIDIA SDK files in this folder.
